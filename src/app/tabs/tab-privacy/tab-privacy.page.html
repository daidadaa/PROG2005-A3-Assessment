This page describes the privacy and security considerations for this Ionic-based Inventory Management application.
1

Data Collection

What information does this app collect?

 ▼

Data Fields:

Item ID — Unique identifier (auto-generated by server) Item Name — Product name (required, must be unique) Category — One of: Electronics, Furniture, Clothing, Tools, Miscellaneous Quantity — Stock count (integer, required) Price — Unit price in dollars (integer, required) Supplier Name — Vendor name (string, required) Stock Status — In Stock / Low Stock / Out of Stock Featured Item — 0 or 1 (default: 0) Special Note — Optional free text field
Note: This app only collects inventory/business data. It does not collect any personal user information, payment details, or location data.
2

Data Storage & Transmission

How is data stored and sent?

 ▼

Storage:

  • All inventory data is stored on a remote server at prog2005.it.scu.edu.au.
  • The app does not use a local database or file storage.
  • Data is accessed through RESTful API endpoints (GET, POST, PUT, DELETE).

Data Flow:

User Input
→
Ionic App
→
REST API
→
Server Database

Offline Cache:

  • The app uses browser localStorage to cache recently fetched items for offline viewing.
  • Cached data expires after 30 minutes to ensure freshness when back online.
  • No sensitive data is persisted permanently on the device.
Security: Since no data is permanently stored locally, there is minimal risk of data exposure if the device is lost or stolen.
3

Input Validation

How does the app validate user input?

 ▼

Client-Side Validation Rules:

FieldTypeValidation
Item NameStringRequired, 1–100 characters, trimmed whitespace
CategoryEnumRequired, one of 5 predefined values
QuantityIntegerRequired, >= 0, whole number only, no leading zeros
PriceIntegerRequired, >= 0, whole number only, no leading zeros
Supplier NameStringRequired, trimmed, max 100 characters
Stock StatusEnumRequired: In Stock / Low Stock / Out of Stock
Featured ItemIntegerOptional, defaults to 0
Special NoteStringOptional, free text

Custom Validators Implemented:

  • Leading Zero Validator: Rejects inputs like "0111", "007", "099" — ensures clean numeric format.
  • Required Field Check: All mandatory fields are validated before form submission.
  • Duplicate Detection: Server returns error (409 Conflict) if item name already exists.
  • Protected Records: Server forbids deletion of certain records (e.g., "Laptop").
Note: Client-side validation improves user experience but server-side validation is also enforced.
4

Access Control

Who can access this application?

 ▼

Current Access Model:

  • The REST API endpoint is publicly accessible without requiring authentication credentials.
  • This is acceptable for an academic assignment where the focus is on mobile UI and API integration.
  • Source code is stored in a private GitHub repository with access limited to team members and the marker.

What Could Be Added in Future:

  • User authentication (login/password or OAuth).
  • Role-based access control (admin vs regular users).
  • API rate limiting to prevent abuse.
5

Mobile Security Considerations

Risks relevant to mobile platforms

 ▼

Device Theft or Loss

Mitigation: No permanent local data storage. All data lives on the server.

Network Interception

All API communication uses HTTPS to encrypt data in transit.

Local Storage Exposure

Mitigation: Offline cache has a 30-minute TTL and contains only non-sensitive inventory data.

Screenshots

Note: The app does not prevent screenshots, which could expose inventory data.
